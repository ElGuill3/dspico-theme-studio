# DSpico Theme Studio MVP

DSpico Theme Studio is an offline Electron application for creating, validating, previewing, and exporting Material and Custom themes. The MVP keeps project files and exports local, requires no AI or cloud service, and validates against the pinned `dspico-launcher-v1` profile.

## Quick path

```bash
pnpm install
pnpm start
```

In the studio:

1. Create a Material or Custom project and edit its theme data.
2. Use undo/redo, save the project, and reopen it from disk.
3. Run diagnostics and inspect the top/bottom preview.
4. Export after all errors are fixed and warnings are acknowledged.

After export, copy the generated `theme/` folder (or extract `theme.zip`) under `/_pico/themes/theme/`, select that folder through the launcher's normal theme setting, and safely eject the SD card. The Studio does not write directly to SD cards and does not make a hardware compatibility claim. When an export contains BGM, keep `bgm.bcstm` inside the exported theme folder at `/_pico/themes/theme/bgm.bcstm`.

## MVP boundary

| Included                      | Not included                                               |
| ----------------------------- | ---------------------------------------------------------- |
| Material and Custom authoring | Raw markup                                                 |
| Local project save/reopen     | Cloud, collaboration, or embedded AI                       |
| Source-backed diagnostics     | Direct launcher-repository or SD-card mutation             |
| 256×192 top/bottom preview    | DS pixel, font, palette, blending, timing, or audio parity |
| Folder and ZIP export         | Packaging, signing, notarization, or auto-update           |

Preview dimensions, bounds, inheritance, wrapping, safe areas, and Material colors are labeled `launcher-vector-backed` where fixtures support them. Browser rendering is labeled `Chromium approximation`. Validation and generated bytes—not visual resemblance—decide export readiness.

## Local trust boundary

- Electron main owns dialogs, project persistence, validation dispatch, hashing, and export writes.
- The renderer is sandboxed with context isolation, no Node integration, a restrictive CSP, and an allowlisted `app://studio` origin.
- Preload exposes only create, open, save, edit, undo, redo, validate, and export commands.
- Navigation, popups, webviews, external/file URLs, and network connections are denied.

## Export outputs

| Output         | Contents                                                    |
| -------------- | ----------------------------------------------------------- |
| `theme/`       | Ready-to-copy theme files and `report.json`                 |
| `theme.zip`    | The same logical files with normalized level-0 ZIP metadata |
| Export summary | Destination, output paths, report SHA-256, and ZIP SHA-256  |

Material exports contain `theme.json`. Custom exports also contain deterministic `topbg.bin` and `bottombg.bin` raster payloads. `report.json` is provenance and verification metadata: it records ordered diagnostics and acknowledgments, file hashes, credits, licenses, sources, and Custom lineage. Its evidence boundary keeps `hardwareParityClaimed: false` deliberately honest. Folder and ZIP are staged, verified, and swapped as one rollback boundary.

### ZIP implementation note

The design preferred pinned `fflate` level 0. Registry DNS was unavailable during implementation, so the MVP uses an internal stored-ZIP writer with fixed metadata and no clock input. Tests prove repeated byte identity and folder/ZIP integrity; replacing it with `fflate` requires preserving those byte-level guarantees.

## Verification

```bash
pnpm test
pnpm typecheck
pnpm lint
pnpm format:check
pnpm test:e2e
pnpm verify:package
```

`test:e2e` builds production renderer/main/preload bundles, launches Electron offscreen on headless Linux, and proves the complete local lifecycle, capability/CSP denials, and export receipt hashes. `verify:package` creates the real Forge package, inspects its ASAR boundary and CSP, then repeats the Material and Custom lifecycle against the packaged executable. `DSPICO_STUDIO_E2E_ROOT` is reserved for that deterministic harness; normal application runs always use native local-file dialogs.
